2026-11-08／**設計のみ・未実装・未承認・配信不可**。Refs #107 / #120 / Draft PR #122。

## 最重要の回答

1. **新版で見えているデータに旧形式由来のデータが残る可能性はある。** 任意field欠落の既定解釈、日時のメモリ内復元、旧形式のrawコピー、旧receiptの保持があり、表示できることは全保存領域の正規化完了を意味しない。本番での実残存件数は未調査。
2. **iPhoneとPCを新版に更新するだけでは安全な切替を保証できない。** 二端末/各origin・旧tabの未同期操作、Journal、旧History、旧receiptとbaselineの対応、writer停止、切替失敗を管理する必要がある。
3. **取得可能な既存原本の不変退避、二端末の棚卸し、意味/件数/原本対応の全件照合、曖昧な旧操作の保全、原子的な世代切替と復旧経路が必要。** 旧アプリを拒否しても旧データは読取/退避/変換対象として残す。既に失われた情報の完全復元を保証するものではない。

## 採用する設計判断

- 方式A「既存の共通同期契約を改善する」を採用。★だけの別同期回避策にはしない。
- **旧writerの恒久混在は終了可能。旧保存形式のサポートは終了しない。** 新契約の使用者は本人、端末はiPhoneとPCの2台。ただしtab/origin/匿名scopeは別途数える。
- 新操作は明示intentと属性ごとの因果基点を持つ。異なる独立属性は合成し、同属性の並行更新は候補を保持して明示解決する。
- 認証された共通受付/reducerを正本のwriterとし、操作/受領/反映・競合を区別する。Nodeは再生成可能な表示投影で、全Node LWWを正本にしない。
- 移行比較は**B「明示的な一度限りの移行」**を推奨。読取互換adapterは残すが、通常起動で暗黙のCloud移行をしない。
- 旧receiptの恒常bridgeは必須とせず、freezeまでに存在する旧データ/操作を移行時に分類・取り込む。後発旧ローカルも限定importで保護する。旧live writeの無期限受理はしない。
- #120の★UI、Rules/Functions/Auth設定、製品コード、データ移行は今回一切実施しない。#119のモード/E2EE設計は別レビューで、このPRへ混ぜない。
